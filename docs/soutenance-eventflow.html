01 · Contexte

Organiser des ateliers à places limitées, sans perdre le fil

Une structure comme BB Numérique propose des ateliers, formations et rencontres. Chaque session a une capacité fixe.

  • Les participants veulent savoir immédiatement s'il reste des places.
  • L'organisateur veut savoir qui est inscrit et à quel événement.
  • Un tableur ou une boîte mail ne se met pas à jour en direct et ne garde aucune trace fiable des actions.

La question du projet

Comment construire une application web où chaque inscription est visible instantanément par tous les utilisateurs connectés, tout en conservant un historique de chaque action ?

Périmètre retenu

  • Deux rôles : administrateur et utilisateur
  • Un cycle complet : créer, publier, s'inscrire, annuler
  • Une application déployée et accessible en ligne
EventFlow · Soutenance
Partir du concret : un atelier de 20 places, 35 personnes intéressées. Avec un tableur, deux personnes peuvent prendre la même dernière place. Insister sur les deux mots clés : instantané et tracé.

03 · Modèle de données

Deux bases pour deux responsabilités

PostgreSQL métier

usersid, email unique, name, password_hash, is_admin, created_at
eventsid, title, description, date, capacity, created_by → users
registrationsevent_id → events, user_id → users, created_at. Clé primaire composite : un utilisateur ne s'inscrit qu'une fois.

Suppression en cascade : effacer un événement efface ses inscriptions. Le nombre d'inscrits est calculé par jointure, jamais stocké.

MariaDB journal

event_logsaction ENUM (event_created, event_updated, event_deleted, user_registered, user_cancelled), event_id, event_title, user_id, details JSON, created_at. Quatre index.
event_statsevent_id, total_registers, total_cancels, last_activity_at. Agrégats dénormalisés, mis à jour à chaque action.

Journal en ajout seul : on n'y modifie jamais une ligne. Il peut grossir et être archivé indépendamment des données métier.

EventFlow · Soutenance
Question probable : pourquoi deux SGBD ? Réponse : séparer les données transactionnelles du journal en ajout seul, qui a un cycle de vie différent, et pratiquer deux moteurs. Le compteur d'inscrits n'est jamais stocké côté PostgreSQL : pas de risque d'incohérence.

04 · Authentification et rôles

      
Un jeton, deux barrières

      

        

          
1ConnexionPOST /auth/loginL'API vérifie l'e-mail et le mot de passe en base et renvoie l'utilisateur et un jeton.

          
2PersistancelocalStorage · auth.hydrate()Le store Pinia conserve la session. Au rechargement, l'utilisateur reste connecté.

          
3Envoi automatiqueAuthorization: BearerUn intercepteur Axios ajoute le jeton à chaque appel, sans le répéter dans les composants.

          
4VérificationrequireAdmin · /auth/meLe serveur relit is_admin en base à chaque écriture. Le client ne décide jamais seul.

        

        

          

            
Barrière client : Vue Router

            
    
              
  • guestOnly : accueil, connexion, inscription. Un utilisateur connecté est redirigé selon son rôle.
    • 
              
  • requiresAuth : redirection vers la connexion avec retour à la page demandée.
    • 
              
  • requiresAdmin : le tableau de bord renvoie un simple utilisateur vers les événements.
    • 
            

          

          

            
Barrière serveur : middleware Express

            
    
              
  • Pas de jeton : 401. Jeton valide mais non admin : 403.
    • 
              
  • Les routes d'écriture sur les événements passent toutes par requireAdmin.
    • 
              
  • L'inscription exige un jeton mais pas le rôle admin.
    • 
            

          

        

        
Choix assumé pour la démonstration : jeton simple de forme user:<id> et mot de passe stocké en clair. Le passage à JWT signé et bcrypt est la première évolution prévue.

      

      
EventFlow · Soutenance

      
Devancer la question sécurité : le jeton n'est pas signé et les mots de passe sont en clair, c'est un choix de démonstration connu et documenté. La protection réelle vient du fait que le serveur revérifie le rôle en base à chaque écriture.

05 · Temps réel

      
Comment ça marche : Server-Sent Events

      

        

          
1Un utilisateur s'inscritPOST /events/:id/registerLe serveur contrôle la capacité puis insère la ligne dans registrations.

          
2Trace dans le journallogActivity()Écriture dans MariaDB, avec le nombre de places restantes en détail JSON.

          
3Diffusionbroadcast()L'API relit la liste complète et l'écrit sur chaque connexion SSE ouverte.

          
4RéceptionEventSource.onmessageLe store Pinia remplace ses items par la liste reçue.

          
5Renduréactivité VueCompteurs, badges et taux de remplissage se mettent à jour.

        

        

          
// server/src/routes/events.js
const clients = new Set();

router.get("/stream", async (req, res) => {
  res.writeHead(200, { "Content-Type": "text/event-stream" });
  res.write(`data: ${JSON.stringify(await listEvents())}\n\n`);
  clients.add(res);
  req.on("close", () => clients.delete(res));
});

          

            
Pourquoi SSE plutôt que WebSocket ?

            
    
              
  • Le flux est à sens unique : le serveur informe, le client agit via REST.
    • 
              
  • HTTP standard : pas de bibliothèque, compatible avec Render et les proxys.
    • 
              
  • Le navigateur se reconnecte seul. En cas d'échec, le store bascule sur une relecture toutes les 5 secondes.
    • 
            

          

        

      

      
EventFlow · Soutenance

      
Le serveur garde un Set des réponses HTTP ouvertes. Après chaque mutation, broadcast() écrit la liste sur chacune. Côté client, EventSource est natif au navigateur. Fallback : relecture toutes les 5 secondes si la connexion SSE échoue.

    


    
    

      
05 · Journal d'activité

      
Tracer chaque action sans jamais bloquer l'application

      

        

          
// server/src/db/mariadb.js — une transaction par action
await conn.beginTransaction();
await conn.query("INSERT INTO event_logs (action, event_id, event_title, user_id, details) VALUES (?,?,?,?,?)", [...]);
if (action === "user_registered")
  await conn.query("INSERT INTO event_stats (event_id, event_title, total_registers) VALUES (?,?,1)
                    ON DUPLICATE KEY UPDATE total_registers = total_registers + 1", [...]);
await conn.commit();

// En cas d'erreur : rollback, puis console.warn — l'API répond quand même.

          
Règle de conception : le journal est un effet secondaire. Une panne de MariaDB ne doit jamais empêcher une inscription. C'est ce qui permet à l'application de tourner sur Render, où MariaDB n'est pas provisionnée.

        

        

          

            
Cinq actions tracées

            

              
                
event_createdcapacité, date

                
event_updatedchamps modifiés

                
event_deletedcapacité

                
user_registeredplaces restantes

                
user_cancelled—

              
            

          

          

            
Lecture

            
GET /events/logs?limit=50 renvoie les dernières lignes. GET /events/stats renvoie les compteurs par événement, triés par dernière activité.

          

        

      

      
EventFlow · Soutenance

      
Une transaction MariaDB par action : la ligne de journal et le compteur agrégé sont écrits ensemble ou pas du tout. L'erreur est avalée volontairement pour ne pas bloquer le métier.

Six problèmes, six correctifs versionnés

      

        
CauseLe site statique ne connaît pas les routes du SPA : il cherche un fichier /events qui n'existe pas.
SolutionFichier _redirects avec la règle /* /index.html 200. Le routeur Vue prend le relais.

        
CauseRender impose son propre port via la variable PORT, ignorée par le code.
SolutionLecture de PORT avant API_PORT, repli sur 3000 en local.

        
CausePort 3307 déjà occupé par Docker Desktop.
SolutionPublication sur 3308. Le port interne 3306 ne change pas.

        
CauseHôte localhost à l'intérieur du conteneur : il désigne le conteneur lui-même.
SolutionNom du service postgres comme hôte et port interne 5432.

        
Causeserver/.env suivi par erreur dès le premier commit.
SolutionRetrait du suivi, ajout au .gitignore, fichier .env.example pour documenter les variables.

        
CauseLe journal était sur le chemin critique : une erreur MariaDB faisait échouer l'inscription.
SolutionlogActivity capture l'erreur et laisse l'API répondre. Le journal est un effet secondaire.

08 · Bilan

      
Ce qui manque encore, et dans quel ordre

      

        

          
Limites actuelles assumées

          
    
            
  • Jeton non signé et mot de passe en clair : acceptable en démonstration, pas en production.
    • 
            
  • Aucun test automatisé, ni côté API ni côté composants.
    • 
            
  • Pas de pagination : la liste complète est renvoyée à chaque diffusion SSE.
    • 
            
  • Journal indisponible en production faute de MariaDB sur Render.
    • 
            
  • Pas de validation de schéma sur les corps de requête.
    • 
          

        

        

          
Perspectives par priorité

          
    
            
  1. Sécurité : JWT signé avec expiration, hachage bcrypt, limitation de débit.
    2. 
            
  2. Qualité : tests Vitest et supertest, pipeline GitHub Actions.
    3. 
            
  3. Données : pagination, validation avec zod, MariaDB hébergée.
    4. 
            
  4. Produit : e-mail de confirmation, liste d'attente quand c'est complet, export CSV des inscrits.
    5. 
            
  5. Diffusion : envoyer seulement l'événement modifié plutôt que la liste entière.
    6. 
          

        

      

      
EventFlow · Soutenance

      
Présenter les limites avant qu'on ne les pointe. Les perspectives sont ordonnées : d'abord la sécurité, ensuite les tests, puis les données, puis les fonctionnalités.
